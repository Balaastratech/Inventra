## 0. What Phase D actually has to produce

Per `AUTONOMOUS_PLAN.md` §Phase D, four deliverables:

1. **Gate 1 stays as it is today** — approve the order, revalidate, create
   the purchase request (`PENDING`, budget reserved). Phase D's own text says
   this gate is "unchanged in shape from today" — Phase D's real work is
   everything after it.
2. **Gate 2 — a genuinely new interrupt** *after* the purchase request
   exists, presenting the drafted vendor email for a separate human
   approval. Approve → send → stamp `vendor_sent_at`/`vendor_send_status`.
   Do nothing → the request sits at gate 2 and later generates a reminder.
3. **Rejection with a recorded reason** at gate 2 — and, per the plan's own
   explicit "same discipline at gate 1" instruction, gate 1 rejections must
   also require and store a reason (a real gap in the current code, found
   this session — see §1).
4. **Reminders** — generated by the sweep (Phase C's `run_sweep`, already
   built) and by opening the pending screen, re-checking freshness first,
   with an escalating reminder count instead of an identical repeat.

Phase D does **not** touch Gate 1's existing mechanics, does not change
Phase C's sweep detection/ranking logic, and does not add a background
scheduler (explicitly Phase H). Phase D's real, load-bearing work is
**splitting `execute_purchase` into two graph stages separated by a real
interrupt**, because today there is no separation at all — see §1.

## 2. Design decisions this plan makes explicit (confirm before coding)

**DD1 — a new `ProposalStatus.AWAITING_VENDOR_APPROVAL` value.** Marks the
pause between "order created" and "vendor emailed." Additive to the existing
enum (no renumbering, no existing value changes meaning) — every place that
currently switches on `ProposalStatus` and doesn't recognize this new value
already has a safe default path (the UI/CLI's `_print_result`/`_render_*`
functions fall through to a generic "unknown status" branch today, confirmed
by reading `app.py::_print_result`'s tail), so this is genuinely additive,
not a breaking enum change.

**DD2 — a new `ProposalStatus.PURCHASE_REQUEST_CANCELLED` value for a
Gate-2 rejection**, distinct from `BLOCKED`. `BLOCKED` today means "the case
could not proceed due to a data/evidence problem" (stale snapshot, no
eligible vendor, etc.) — semantically wrong for "a human deliberately
declined to send this order to the vendor after already approving its
creation." Reuses the exact same `cancel_purchase_request` mechanism Gate
1's existing cancel-a-`PENDING`-order path already has (see DD paragraph in
§4), so no new cancellation logic, only a new terminal label on the case
graph side.

**DD3 — reminder tracking lives on `purchase_requests`, not on a new table.**
The enduring record of "this request has been waiting at gate 2" is the
`purchase_requests` row itself (it already exists by the time gate 2 is
reached — it was written by the node that used to be the second half of
`execute_purchase`). New columns: `vendor_reminder_count INTEGER DEFAULT 0`,
`vendor_last_reminded_at TIMESTAMP`. Additive via `migrate.py`'s existing
`_ADDITIVE_COLUMNS` mechanism (Phase A/B/C's own established pattern — no
new mechanism needed, this is exactly what that list is for).

**DD4 — `execute_purchase` is split into two nodes: `execute_purchase`
(unchanged name, now ONLY creates the purchase request and stops — no vendor
email logic at all) and a new `request_vendor_approval` /
`await_vendor_approval` pair (mirroring the existing
`request_approval`/`await_approval` pair's shape exactly).** This is the
single largest code change in Phase D and the plan is explicit that it
should copy the *existing* Gate-1 pattern line for line, not invent a new
shape: a deterministic node that drafts what the human will see and emits
an audit event (`request_vendor_approval`, mirroring `request_approval`),
then a thin `interrupt()`-only node (`_await_vendor_approval`, mirroring
`_await_approval`) that validates the resume payload and hands off to a new
`nodes.handle_vendor_decision(state, decision)` function (mirroring
`nodes.handle_decision`).

**DD5 — Gate 2's `ApprovalDecision`-equivalent is a new, small model
(`VendorSendDecision`), not a reuse of `ApprovalDecision`.** Reusing
`ApprovalDecision` would drag in fields that mean nothing here
(`edited_offer_id`, `chosen_target_basis` — Gate 2 offers no supplier
switch, no target-basis switch, only send/reject). New model in
`domain/tool_models.py`, matching `ApprovalDecision`'s existing style:
`request_id: str`, `case_id: str`, `decision: str` (`"APPROVED" | "REJECTED"`
only — no `REVISE`, no `EDIT`, Gate 2 has no "ask for changes" concept, the
order is already fixed), `approver: str`, `reason: Optional[str]` (required
when `decision == "REJECTED"`, enforced by a Pydantic validator — this is
where DD-"same discipline"'s reason requirement is actually enforced for
Gate 2), `approved_at: datetime`.

**DD6 — Gate 1's existing `ApprovalDecision` gains a validator requiring
`comments` when `decision == "REJECTED"`.** This is the "same discipline at
gate 1" fix named in §1. A **behavior change to an existing, shipped path**
— flagged explicitly, not silently bundled with Gate 2's new work, since it
changes what a currently-valid API call (`resume_case(case_id, "REJECTED",
approver)` with no comment) will now reject. The UI's existing "Reject"
button also needs its `disabled=` condition updated to require the comment
field non-empty, matching how "Ask for changes" already works.

**DD7 — the reminder *send* itself reuses `notifications/email.py`'s
existing pattern (a new `notify_vendor_approval_needed(state)` /
`notify_vendor_approval_reminder(...)` function), not a new email module.**
`vendor_email.py` stays exactly what it is today — the outbound message TO
the vendor. The Gate 2 approval request and its reminders are inbound-facing
notifications TO the human approver, so they belong in `email.py` alongside
`notify_awaiting_approval` (Gate 1's equivalent), following that file's exact
existing conventions (`_esc`, `_money`, `send_email`, fire-and-forget
failure handling).

**DD8 — Gate 2's email approval links reuse `tokens.py` unchanged**, with
one new `decision` value the token payload can carry (`"REJECTED"` already
supported generically — no schema change to the token itself, since
`make_token`/`verify_token` never hardcoded gate-1-specific semantics). A
new pair of routes on `approval_server.py`'s existing `app` (same file, same
`FastAPI` instance) — not a second server, not a second port.

## 4. Task-by-task plan

### Gate 1 — confirm unchanged shape, add the reason requirement (DD6)

Per the source plan: "Unchanged in shape from today." Confirmed true for the
approve/revalidate/create-purchase-request path. The **one** required change:

```python
# domain/tool_models.py, ApprovalDecision

@model_validator(mode="after")
def _rejection_requires_a_reason(self) -> "ApprovalDecision":
    if self.decision == "REJECTED" and not (self.comments or "").strip():
        raise ValueError("A reason is required to reject a proposal.")
    return self
```

This raises at the same point every other `ApprovalDecision` validation
error already surfaces (Pydantic construction, inside `_await_approval` /
`approval_server.execute` / `app.py::resume_case`) — no new error-handling
path needed, it fails the same way a malformed decision payload already
does today (confirmed: `_await_approval` calls
`ApprovalDecision.model_validate(decision_payload)` directly, uncaught
ValueError would propagate — **verify at implementation time whether that
propagation is already handled gracefully somewhere upstream, or whether
this task also needs a try/except added around that specific call site**,
since a raised exception inside a LangGraph node has different failure
semantics than a `_fail(state, ...)` call; this is flagged, not assumed).

`submission/ui.py`'s existing Gate-1 "Reject" button:
```python
# before: if st.button("Reject", disabled=not ready, ...)
# after:
if st.button("Reject", disabled=not (ready and comment.strip()), use_container_width=True):
```
Matches "Ask for changes"'s existing pattern exactly (same file, a few lines
above).

`submission/app.py`'s CLI already passes `comments` through unchanged — no
CLI signature change needed, the new validation happens inside the Pydantic
model itself, so every caller (CLI, UI, email approval server) is protected
by one shared check.

### Gate 2 — the new interrupt (the core of this phase)

**Step 1 — split `execute_purchase`.**

```python
# submission/graph/nodes.py

def execute_purchase(state: CaseState) -> CaseState:
    """UNCHANGED apart from deleting the vendor-email branch at the end.
    Creates the purchase request, reserves budget, emits the audit event --
    exactly as today. Vendor notification is no longer this node's job."""
    proposal = state["proposal"]
    idempotency_key = state.get("idempotency_key") or proposal.proposal_hash
    state["idempotency_key"] = idempotency_key
    result = create_purchase_request(proposal=proposal, idempotency_key=idempotency_key,
                                       approved_by=state["approval_decision"].approver)
    state["purchase_result"] = result
    emit_audit(state, "system", "purchase_request_created" if result.error is None else "write_failed",
               {"request_id": result.request_id, "created": result.created,
                "error": result.error.value if result.error else None})
    if result.error is not None:
        _fail(state, result.error, result.error_details or "Write failed")
    else:
        state["status"] = ProposalStatus.PURCHASE_REQUEST_CREATED
    return state
    # NOTE: the "if config.vendor_email_enabled: send_purchase_order(...)"
    # block that used to live here is DELETED, not moved verbatim -- its
    # logic is now split between request_vendor_approval (drafts) and
    # handle_vendor_decision (actually sends on APPROVED).


def request_vendor_approval(state: CaseState) -> CaseState:
    """Deterministic. Drafts what the human will see at Gate 2 -- the exact
    vendor-facing message content, so the approver reviews what will
    actually be sent, not a paraphrase of it. Mirrors request_approval's
    shape (that function also just prepares + emits audit; the pause
    itself lives in the *next* node, same as Gate 1)."""
    state["status"] = ProposalStatus.AWAITING_VENDOR_APPROVAL
    emit_audit(state, "system", "vendor_approval_requested",
               {"request_id": state["purchase_result"].request_id})
    return state


def handle_vendor_decision(state: CaseState, decision: "VendorSendDecision") -> CaseState:
    state["vendor_send_decision"] = decision  # NEW CaseState field
    emit_audit(state, f"human:{decision.approver}", "vendor_decision_recorded",
               {"decision": decision.decision, "reason": decision.reason})
    if decision.decision == "REJECTED":
        result = cancel_purchase_request(state["purchase_result"].request_id, decision.approver, decision.reason)
        state["cancellation_result"] = result  # NEW CaseState field, for the UI/audit trail
        record_signal("vendor", state["proposal"].recommended_vendor_id, "gate2_rejected",
                       decision.reason, source_case_id=state["case_id"])
        state["status"] = ProposalStatus.PURCHASE_REQUEST_CANCELLED
        return state
    # APPROVED
    try:
        sent = send_purchase_order(state["proposal"], state["purchase_result"])
        emit_audit(state, "system", "vendor_send_attempted", {"sent": sent})
    except Exception as e:
        emit_audit(state, "system", "vendor_send_failed", {"error": str(e)})
        # Per the existing execute_purchase discipline this replaces: a
        # vendor-send failure must NEVER flip "order placed" back to
        # something else -- the internal purchase_requests write already
        # happened in an earlier, separate node. Status stays
        # PURCHASE_REQUEST_CREATED either way; only vendor_send_status
        # (already tracked by mark_vendor_send_status inside
        # send_purchase_order itself) records the send outcome.
    state["status"] = ProposalStatus.PURCHASE_REQUEST_CREATED
    return state
```

```python
# routes.py
def route_after_execution(state: CaseState) -> str:
    result = state.get("purchase_result")
    if result is None or result.error is not None:
        return "write_failed"
    from submission.config import config
    return "success_with_vendor_gate" if config.vendor_email_enabled else "success_no_vendor_gate"

def route_after_vendor_decision(state: CaseState) -> str:
    decision = state.get("vendor_send_decision")
    return "cancelled" if decision is not None and decision.decision == "REJECTED" else "sent"
```

**Why the gate is config-conditional, not always-on:** `config.vendor_email_enabled`
already defaults `False` pending the SPF/DKIM/DMARC go-live review (D12's own
documented reason). If Gate 2 always paused the graph even with vendor email
disabled, every case would stop one step short of `finalize_success` for a
send that will never happen — a new dead-end for every existing test and demo
that doesn't configure vendor email. Conditioning the *routing* (not the node
definitions) on the existing flag means: vendor email off (today's default,
and every existing test's default) → behavior is **exactly** what it is
today, `execute_purchase` → `finalize_success`, no new pause ever appears.
Vendor email on → the new two-node gate is exercised. This is the same
"backward compatible by construction" discipline `PHASE_B_PLAN.md`'s B10
task used for `evaluate_options(inputs=None)`.

**Extending `check_in_flight_case`** (`submission/sweep/resweep.py`):
```python
def check_in_flight_case(sku: str, warehouse_id: str) -> ReminderAction | None:
    from submission.portfolio import list_pending_cases
    for item in list_pending_cases():
        if item.get("sku") != sku or item.get("warehouse_id") != warehouse_id:
            continue
        status = item.get("status")
        if status == "AWAITING_APPROVAL":
            if item.get("likely_stale"):
                return ReminderAction("REVALIDATION_NEEDED", item["case_id"], item["thread_id"], "...")
            return ReminderAction("REMINDER", item["case_id"], item["thread_id"], "...")
        if status == "AWAITING_VENDOR_APPROVAL":  # NEW
            if item.get("likely_stale"):
                return ReminderAction("VENDOR_SEND_REVALIDATION_NEEDED", item["case_id"], item["thread_id"],
                    "This purchase order needs re-validation before the vendor email can be sent -- "
                    "facts may have changed since it was approved.")
            return ReminderAction("VENDOR_SEND_REMINDER", item["case_id"], item["thread_id"],
                "A human can approve sending the vendor email, or reject with a reason.")
        return None
    return None
```

**Note on "revalidation" for a Gate-2 pause**: unlike Gate 1 (which has a
real `revalidate` node re-checking stock/offer/budget before writing), there
is currently **no equivalent re-check for Gate 2** — the order already
exists by the time Gate 2 is reached, so "facts changed" mostly means "did
the vendor's contact email change, did the offer they're being sent against
still exist" rather than the stock/budget facts Gate 1 revalidates. This
plan does **not** propose building a Gate-2-specific revalidation node — it
reuses the same `likely_stale` staleness signal `list_pending_cases()`
already computes (time-since-pause vs `config.data_freshness_hours`) as a
conservative proxy, exactly as C5 already does for Gate 1. Flagged as a
scope-narrowing decision (§9), not silently assumed to be equivalent to a
real revalidation.

## 9. Open questions this plan surfaces (confirm before implementation)

- **New — does a Gate-1 rejection also need an `agent_memory_signals` write?**
  This plan reads the source plan's text as scoping that specifically to a
  vendor being rejected (which only happens at Gate 2, since Gate 1 rejects
  the *order*, not the *vendor choice*) — but the source plan's own
  "Rejection with a recorded reason" section header covers both gates, and a
  future demand-side memory signal (e.g. "this SKU's automated reorder was
  rejected twice") is arguably just as valuable as a vendor-side one. Not
  built in this plan; flagged for a decision before implementation.
- **New — is `notify_blocked`'s generic template good enough for
  `finalize_vendor_cancelled`, or does a Gate-2-cancellation deserve its own
  wording** (e.g. explicitly distinguishing "the order still exists and
  reserved budget was released" from a data-caused block, which a human
  reading a generic `notify_blocked` email might misread as "nothing
  happened")? This plan defaults to reuse (§4) but flags it as a
  presentation decision, not an architectural one — cheap to change later
  either way.
- **New — the exact propagation behavior of a raised `ValueError` from
  `ApprovalDecision.model_validate(...)` inside `_await_approval`** (DD6's
  validator) needs to be traced at implementation time, not assumed. If it
  currently propagates uncaught out of the interrupted node, this plan's
  Gate-1 change might need an accompanying try/except added at that exact
  call site so a rejected-without-a-reason attempt fails as a clean,
  user-facing message rather than an unhandled exception inside the graph.
  Flagged explicitly in §4 rather than assumed either way.
- **New — should the Gate-2 email approval link reuse `approval_server.py`'s
  existing single `app` and port**, or does routing two different
  "gates" through one `/decide` endpoint (discriminated by a new `"gate"`
  field on the token payload, per DD8) risk future confusion versus a
  clearly separate `/decide-vendor-send` path? This plan defaults to one
  endpoint with a discriminator (matches the existing file's own "REVISE
  gets a form, APPROVED/REJECTED get a confirm button" branching pattern,
  which already discriminates on `decision` inside one endpoint) — flagged
  as the chosen approach, not silently assumed to be the only option.
